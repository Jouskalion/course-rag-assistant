# AI 审查与合并规则

日常合并使用 Codex 自动代码审查加 GitHub 自动构建，不要求固定同伴人工审批。仓库采用“自动审查开启、所有 PR、每次推送时触发；自动安全审查关闭”的配置。“全面审查”目前沿用个人偏好，不能据此认定为开启或关闭。网页设置控制触发方式，本文件和 AGENTS.md 提供项目约定；普通构建通过不能标成 AI 审查通过。

普通自动审查实际运行时会产生 Codex 用量。提交者把相关小修改整理好后再推送，避免反复触发；无需在自动审查运行时重复发送手动审查请求。

## 提交者操作

1. 在任务分支提交代码，创建 PR，写明任务编号与负责人。main 设置为受保护分支，必须通过 PR 合并，禁止直接推送、强制推送和删除。
2. 等待 Codex 自动审查，并在 PR 或关联的 Codex 任务中查看结果。审查依据本文件、AGENTS.md、PR 差异和相关接口及调用方代码。仅在自动审查未触发或需要补充检查时，在 PR 评论中使用 `@codex review`；手动审查也产生用量。
3. 核对结果对应的提交版本。任何新提交后等待本次审查完成，不能沿用旧提交的通过结论。未看到问题评论不等于已经审查完成；查看机器人反馈或任务状态确认。
4. 修复审查问题，确认 GitHub 的 `build` 和 `codex-review` 两项必需检查都通过。`build` 包含合并门禁验证、契约一致性、Java 编译打包、TypeScript 检查与前端构建。
5. 当前版本两项检查通过、分支已包含最新 main、PR 讨论已解决后，由有写入权限的成员 Squash 合并。不要求固定同伴人工审批。保护规则同样约束仓库管理员；普通 AI 自动审查本身不会自动合并。
6. 涉及公共接口、数据库结构、依赖版本或模块职责变化时，先提出影响说明与设计修订，由小组决定是否改变已定方案，再按新约定审查。没有结构变化的普通合并不增加此步骤。

## 审查尺度与分阶段交付

正式审查问题应聚焦功能、公共接口、数据库、模块架构和数据安全，并有具体代码位置、触发条件及影响作为依据。已经冻结的设计仍须遵守，结构变更仍按前述小组确认和设计修订流程处理。

纯排版、局部变量命名偏好、注释多少、等价写法或非必要重构，不作为正式审查问题；用户明确要求时，可作为非阻断建议另行提出。例如“这个局部变量换个名字更好看”属于偏好，而修改约定的公共字段导致前后端不兼容属于实质问题。已有契约、类型和构建检查仍必须通过。

成员可以按各自分工逐步提交，不要求每个 PR 完成整个系统。明确尚未交付的其他模块骨架、已有 501、后续安排的完整系统测试与样例数据，不应单独阻断当前 PR；但本 PR 交付路径仍未实现、伪装成功或造成已有功能回归时，仍需修复。

本次调整的是 AI 选择和表述正式问题的标准。门禁仍要求当前提交的审查已完成且没有正式问题，脚本不会按评论文字或严重级别自动忽略问题。遇到疑似误报，应补充接口约定、复现条件等证据，必要时澄清规则并重新审查；仅点击“已解决”或刷新现有结果不能代替重新审查。

## AI 必查内容

- 文件是否放在正确模块，是否重复公共类型，是否绕过接口直接依赖其他模块实现类。MyBatis-Plus 只允许出现在 B 的 documents/db 模块，pom 依赖版本须与 docs/DECISIONS.md 一致，不得绕过 CourseLocks/WriteTransactions。Lombok 仅用于 B 的 entity，版本须与 docs/DECISIONS.md 一致，不得用于生成的 DTO。
- HTTP路径、方法、字段、默认值、可空性、枚举、返回码是否与openapi一致，前后端生成类型是否同步。
- 数据结构、外键、迁移、UUID、UTC时间、页序、Unicode码点规则是否一致。
- 范围过滤是否先于Top-k；是否混入其他课程或未选择资料；会话范围是否被静默修改。
- 资料是否在向量齐备前发布ready；删除、停用、重试和缓存是否一致；快照是否被提前释放。
- 来源是否取自真实片段；引用是否由后端映射；模型输出是否经过校验；调用失败是否被伪装成资料不足。
- 是否出现请求重复执行、问答状态乱序、晚到覆盖终态、写事务内网络等待或共享JDBC连接。
- 是否提交密钥、数据库、原课件、node_modules、构建产物；是否擅自增加服务、数据库或账号体系。
- 是否还包含已接入路径上的501未实现入口；若任务尚未交付必须明确记录，不能称功能完成。

## 强制合并检查

`codex-review` 由 `.github/workflows/codex-review-gate.yml` 维护，只读取原生 Codex 机器人已经发布的代码审查结果，不调用模型，不额外产生 Codex 审查用量。自动安全审查仍保持关闭。保护设置把 `build` 和 `codex-review` 都限定为 GitHub Actions 发布的检查。

门禁核对机器人身份、发布应用、最后编辑者，以及结果是否对应 PR 当前完整提交 SHA。仅当代码审查已完成且没有报告问题时通过；审查未开始、运行中、对应旧提交、有问题、格式无法识别或读取失败都会阻止合并。等待期间显示未通过，Codex 更新结果后自动重新核对；不能靠手动点击“已解决”把有问题的审查变成通过。

这项有写入检查权限的工作流只执行 main 上的脚本，不执行 PR 分支代码。若结果更新后检查仍未刷新，可在 Actions → Codex review gate → Run workflow 输入 PR 编号重新读取结果；该操作不请求新的 AI 审查。若机器人结果格式发生变化，需要修复适配脚本，不能关闭门禁绕过。

门禁使用 GitHub 提交状态直接绑定当前 SHA，不依赖某一轮工作流的检查记录。PR 事件、机器人评论更新和手动刷新都会重新核对并更新同一项 `codex-review` 状态，重复触发不需要再次提交代码。PR 中必须看 `build` 和 `codex-review`，不能把辅助工作流 `refresh-gate` 执行成功当作 AI 审查通过。

这些验证只检查合并门禁本身，不是项目功能测试或完整系统测试。主分支保护由 GitHub 仓库设置执行，不能仅靠本文件实现；仓库所有者仍有修改仓库设置的管理权限。

## 审查结果与补充手动审查

GitHub 原生自动审查使用 Codex 的标准反馈形式，重点报告可定位的高优先级问题；不要求机器人另写一份固定格式的长报告。问题应说明文件位置、影响及修复建议。格式、生成代码一致性和编译结果交给相应工具检查；没有执行的检查不得推断通过。审查建议不等于系统功能已经测试通过。

如果需要在 Codex 中补充手动审查，可使用以下指令，并将结果与对应提交版本关联：

> 请依据 AGENTS.md 和 docs/AI_REVIEW.md，审查本分支相对 main 的全部修改及相关调用方。核对接口、数据库和目录职责，检查关键业务规则，不只检查格式。只报告有依据、可定位的实质问题，不把纯风格偏好或计划后续交付的其他模块当作正式问题，并记录当前提交SHA。可以运行契约、编译和构建检查；本阶段不要创建样例数据或完整测试方案。先给问题列表，再说明是否存在阻断合并的问题。未经授权不要改公共设计或合并PR。

自动工作流只提供构建和生成类型一致性结果，不能证明答案语义正确，也不能替代 AI 审查。完整系统测试及题集稍后独立安排。
